# AGENTS.md

## 一、核心工作原则

1. 开始实现前，必须结合以下信息完整理解任务：

   * 用户当前请求与对话上下文；
   * 仓库中适用的 `AGENTS.md`；
   * 相关 `DEV_OVERVIEW.md`；
   * 相关 `PRD.md`；
   * 现有代码、测试、README、接口定义及其他必要文档。

2. 项目文档的默认阅读顺序为：

   1. `DEV_OVERVIEW.md`：理解项目背景与整体方向；
   2. `PRD.md`：理解细化需求及其实现状态；
   3. 代码与测试：确认当前真实行为。

3. `DEV_OVERVIEW` 和 PRD 的“未实现”内容只提供方向与需求背景，不自动构成立即开发、排期或交付承诺。只有用户当前明确要求实施时，才进入开发流程。

4. 用户当前请求定义本次任务，但不得静默覆盖既有方向或已确认需求。若请求与相关 `DEV_OVERVIEW`、PRD、接口约束或现有行为存在冲突、歧义或关键缺口，应先结构化整理并向用户确认，再开始实现。

5. 优先保持实现简洁、清晰、可验证，避免过度设计和无关重构。

6. 不得把推测、临时讨论或未经用户确认的设想写成既定方向或需求。无法确定的内容应保留为待确认问题。

## 二、项目文档体系

| 文档或来源 | 主要职责 | 回答的问题 |
|---|---|---|
| `AGENTS.md` | 工作方式、流程、工具、测试和文档维护规则 | Codex 应该如何工作 |
| `DEV_OVERVIEW.md` | 项目背景、整体目标、开发方向、跨模块原则和全局约束 | 项目为什么这样发展、整体上往哪里走 |
| `PRD.md` | 具体需求及其“已实现 / 未实现”状态 | 具体需要什么、当前实现到了哪里 |
| 代码与测试 | 当前实现行为及验证结果 | 系统现在实际上如何工作 |

信息归属规则：

* 整体背景、长期目标、跨模块方向和项目级约束放入 `DEV_OVERVIEW`；
* 可执行、可验收的具体需求放入 PRD；
* 普通实现过程和低层代码细节不写入需求文档；
* 临时分析、中间方案和调研资料放入 `./local_docs`；
* 同一信息只保留一个主要归属位置，其他文档通过索引或简要引用关联。

若文档与代码不一致，不得直接假定任一方正确。应结合用户要求、测试、提交历史和相关上下文判断，必要时向用户确认。

## 三、文档定位与读取

当前环境未配置专用的 DEV_OVERVIEW 或 PRD 查找工具。读取具体文档前，应先通过仓库检索定位。

确认仓库根目录：

```bash
git rev-parse --show-toplevel
```

定位方向文档：

```bash
find . -name "DEV_OVERVIEW.md" \
  -not -path "./.git/*" \
  -not -path "./.venv/*" \
  -not -path "./node_modules/*"
```

定位需求文档：

```bash
find . -name "PRD.md" \
  -not -path "./.git/*" \
  -not -path "./.venv/*" \
  -not -path "./node_modules/*"
```

也可以结合 `rg`、`ls`、目录结构和文件内容判断相关性。

读取时：

1. 先读根级 `DEV_OVERVIEW.md`，再读相关子级文档；
2. 再读根级 `PRD.md`，再读相关子级文档；
3. 不要只凭文件名判断，应检查实际内容；
4. 不要为了“完整”读取所有无关文档；
5. 文档不存在时，应在确有需要时按下述规则创建，而不是跳过需求理解。

## 四、DEV_OVERVIEW 规则

### 1. 职责

`DEV_OVERVIEW` 用于补足开发者通过长期沟通自然获得、但 Codex 基础工作环境中缺失的项目级上下文。它应记录：

* 项目的业务或技术背景；
* 当前阶段的主要目标；
* 中长期开发方向；
* 跨模块的设计原则与全局约束；
* 已确认但不一定立即实施的整体调整；
* 对后续开发持续有效的关键判断；
* 项目级未知问题或待决策事项。

它不用于记录：

* 单个函数、字段或接口的细节；
* 具体任务清单、排期或开发日志；
* 每次提交的修改摘要；
* 已实现功能的完整列表；
* 未经确认的发散想法；
* 只从代码即可得出的低层实现细节。

### 2. 文件树

* 仓库根目录维护根级 `DEV_OVERVIEW.md`；
* 某一业务域、系统或模块的方向性内容形成独立维护边界时，可在对应子目录维护子级 `DEV_OVERVIEW.md`；
* 子级文档开头保留简要父级上下文；
* 父级文档增加子文档索引与简要说明；
* 只有在根级文档明显过长、主题混杂或边界不清时再拆分。

建议结构：

```markdown
# DEV_OVERVIEW

## 项目背景

## 当前目标与开发方向

## 全局原则与约束

## 中长期方向

## 关键未知与待决策事项

## 子文档索引
```

### 3. 方向沟通与 `$dev-commute`

当用户提供以下内容时，必须调用 `$dev-commute`：

* 项目整体目标、定位或开发方向；
* 跨模块架构原则、业务约束或优先级调整；
* 对未来开发持续有影响、但当前不一定立即实施的要求；
* 对既有项目认知的纠正、替换或补充；
* 明确要求记录或同步项目开发背景。

即使用户没有点名 skill，只要请求实质上属于项目方向沟通，也应隐式调用。

如果同一次沟通还包含已确认的具体功能、接口、行为边界、依赖关系、验收标准或开发计划细节，应同时更新相关 PRD 的“未实现”部分。

方向沟通本身不意味着立即编码。用户只要求记录时，只修改文档。

### 4. 开发完成后的更新阈值

普通开发完成后，不要机械更新 `DEV_OVERVIEW`。只有满足以下任一条件时才调整：

1. 用户已确认的新方向使现有 `DEV_OVERVIEW` 出现明显矛盾或过时描述；
2. 本次改动形成了原文档未覆盖、且达到项目级颗粒度的新方向，例如跨模块职责、核心架构边界、长期产品定位或全局开发原则发生变化。

局部功能、普通 bug 修复、现有方向内的自然扩展、内部重构或单纯实现方式变化通常不更新 `DEV_OVERVIEW`。

## 五、PRD 规则

### 1. 基本结构

PRD 保存具体需求及其当前实现状态。每个 PRD 必须明确包含：

```markdown
## 已实现

## 未实现
```

可以增加“上下文与范围”“子文档索引”等辅助章节，但不得模糊两个状态的边界。

### 2. “已实现”

记录已经通过代码修改和必要验证落地的需求事实，包括：

* 当前具备的功能与行为；
* 已生效的接口、数据结构、约束和边界；
* 对后续开发持续有影响的兼容性或异常行为；
* 必要的稳定验证说明。

要求：

* 只能根据实际代码和验证结果记录；
* 以需求和外部行为为中心，不写开发日志；
* 临时调试方法和无长期价值的实现细节不写入；
* 只完成一部分时，只记录已完成部分。

### 3. “未实现”

记录用户已确认、但尚未完成开发的细化需求，包括：

* 功能行为与业务规则；
* 输入、输出、接口和数据约束；
* 验收标准与关键边界；
* 与其他模块的依赖关系；
* 已确认的开发计划细节；
* 尚需用户决定的问题。

要求：

* “未实现”不表示已经排期或承诺交付；
* 只记录已确认内容，不把推测写成要求；
* 未确定内容明确标记为“待确认”，并说明影响；
* 颗粒度应足以指导后续开发，但不要过早固化无必要的内部代码结构；
* 原则上应能关联到 `DEV_OVERVIEW` 的整体方向。

### 4. 文件树与旧文档迁移

* 根目录维护根级 `PRD.md`，描述项目整体需求和子文档索引；
* 模块需求形成独立边界时，在对应子目录创建子级 `PRD.md`；
* 子 PRD 说明父级背景、当前范围及与其他模块的关系；
* 父 PRD 增加子文档索引；
* 不在多个 PRD 中重复维护同一需求正文。

建议结构：

```markdown
# <项目或模块> PRD

## 上下文与范围

## 已实现

## 未实现

## 子文档索引
```

旧 PRD 尚未区分状态时，在下一次相关更新中逐步分类：

* 保留原始需求含义；
* 无法确认状态的内容不得直接归入“已实现”；
* 若全量迁移会扩大任务范围，只迁移本次涉及的部分并在总结中说明。

## 六、任务路由

### 1. 项目方向沟通

用户主要是在提供背景、整体要求、方向调整或未来规划，且未要求立即开发时：

1. 调用 `$dev-commute`；
2. 读取相关 `DEV_OVERVIEW` 和 PRD；
3. 更新方向文档，并在必要时更新 PRD“未实现”；
4. 只修改文档，不修改业务代码；
5. 说明记录内容、冲突和待确认事项。

### 2. 明确开发任务

用户要求实现、修改、修复、重构或验证功能时：

1. 先读相关 `DEV_OVERVIEW`；
2. 再读相关 PRD 的“已实现”和“未实现”；
3. 检查当前请求与既有方向、需求和行为是否一致；
4. 明确范围、验收标准、依赖和非目标；
5. 存在冲突或关键歧义时先确认；
6. 完成设计、实现、检查、测试和文档同步。

### 3. 同时包含方向调整与开发要求

1. 先用 `$dev-commute` 归档新方向和未实现需求，并检查冲突；
2. 无冲突或覆盖关系已明确时，再进入开发流程；
3. 有冲突且覆盖关系不清时，先确认，不得一边按旧方向实现、一边直接写入新方向。

### 4. 一般分析或问答

* 答案依赖项目背景时读取相关文档；
* 不因一次问答自动修改文档；
* 只有当用户形成新的项目方向或已确认需求时，才进入文档更新流程。

## 七、开发任务工作流程

1. **重新理解任务**

   结合用户请求、对话上下文、相关 `DEV_OVERVIEW`、PRD、代码和测试，形成明确任务定义。

2. **明确范围**

   至少确认：目标问题、预期行为、验收标准、影响范围、必须保持的行为、依赖和非目标。

3. **检查一致性**

   对比当前请求与：

   * `DEV_OVERVIEW` 的整体方向；
   * PRD“已实现”的现有行为；
   * PRD“未实现”的已确认需求；
   * 当前代码和测试。

   发现冲突、关键歧义或无法自行判断的设计选择时，结构化说明并向用户确认。

4. **制定方案**

   选择最简单、局部、可验证的方案。涉及复杂依赖、新框架、外部服务或高风险迁移时，先做小范围验证。

5. **使用 subagent**

   分配子任务时必须提供：

   * 整体需求和当前子任务目标；
   * 相关 `DEV_OVERVIEW` 与 PRD 上下文；
   * 直接影响任务的上游信息；
   * 与其他子任务或下游实现的兼容性要求；
   * 预期输出与验证方式。

6. **执行实现**

   * 阅读直接相关的代码与一手资料；
   * 遵循项目已有风格；
   * 在当前范围内完成实现；
   * 避免无关重构；
   * 对关键行为补充必要测试。

7. **检查与修复**

   主 agent 检查需求满足情况、逻辑与兼容性、异常处理、类型、代码风格，以及 subagent 结果与整体方案的一致性。存在问题时继续修复。

8. **端到端验证**

   将需求拆分为核心业务路径逐项验证，优先验证真实业务流程，而不是只验证孤立函数。

9. **同步文档并总结**

   按下一节更新 PRD，判断是否达到更新 `DEV_OVERVIEW` 的阈值，并向用户报告结果。

## 八、开发完成后的文档同步

### 1. PRD 更新决策

| 本次情况 | “已实现”处理 | “未实现”处理 |
|---|---|---|
| 新开发内容与现有“未实现”无关 | 增加实际完成的需求 | 不修改 |
| 完整实现某条“未实现”需求 | 整理进“已实现” | 删除或迁出已完成内容 |
| 只实现某条需求的一部分 | 只记录已完成部分 | 保留剩余部分并调整边界 |
| 经用户确认改变原需求 | 记录最终实际行为 | 同步修订剩余要求 |
| 没有代码行为变化 | 不更新 | 仅在形成新确认需求时更新 |

只要调整了 PRD 的“未实现”部分，最终总结必须明确说明：

* 哪些条目被修改；
* 哪些内容迁移到“已实现”；
* 哪些内容仍保留；
* 是否改变原需求边界；
* 调整依据是实际实现、用户确认还是范围拆分。

不得只笼统说明“已更新 PRD”。

### 2. DEV_OVERVIEW 更新决策

完成代码后判断：

1. 当前实现是否与现有整体方向明显冲突；
2. 用户是否已明确改变项目级方向；
3. 本次改动是否形成跨模块或长期有效的新约束；
4. 其颗粒度是否足以进入 `DEV_OVERVIEW`。

只有满足第四节阈值时才更新。否则保持不变，并在总结中说明本次改动位于现有方向之内。

### 3. 文档质量

更新文档时必须：

* 将内容融入现有结构，不追加对话日志；
* 删除或改写失效、重复或矛盾表述；
* 使用稳定、清晰、可验证的需求语言；
* 不声称未验证的行为已实现；
* 检查父子文档索引是否正确。

## 九、subagent 返回要求

subagent 完成后应返回：

* 完成内容与关键方法；
* 修改文件；
* 测试或验证结果；
* 当前可能并非最优的设计决策；
* 未知问题、未解决疑问或风险；
* 与上游要求及下游兼容性的说明。

主 agent 必须结合实际 diff 判断其是否符合子任务、整体需求、相关 `DEV_OVERVIEW`、PRD 和项目设计。结果不理想时直接修正或重新派发。

## 十、工具与依赖

涉及不熟悉的工具或依赖时，优先阅读：

* 官方文档；
* 依赖源码；
* 项目 README；
* 类型定义；
* 官方示例。

不要在未理解关键行为、配置方式和边界条件前集成。复杂工具、新框架或外部服务应先小范围验证。

添加生产依赖前，确认现有依赖是否已能解决、引入和维护成本、版本兼容性，以及是否需要用户确认。

## 十一、测试

针对 Python 项目：

* 使用 `pytest`；
* 可行时优先使用真实数据进行端到端测试；
* 覆盖核心需求、复杂路径和高风险边界；
* 测试数量精简但高价值；
* 测试文件放置在 `./tests`，必要时按模块拆分。

每个测试文件开头需说明覆盖内容和运行命令：

```python
"""
Covers:
- xxx feature behavior
- xxx edge case

Run:
    uv run pytest tests/test_xxx.py
"""
```

测试后记录实际结果。因环境、权限、外部服务或数据缺失无法执行时，明确说明未验证范围和风险，不得声称通过。

## 十二、包管理

Python 项目统一使用 `uv`：

```bash
uv sync
uv run pytest
uv add <package>
```

不要在未确认项目约定前混用 `pip`、`conda`、`poetry` 等工具。现有项目已明确使用其他工具时，遵循更具体的项目约定。

## 十三、目录约定

* `./local_docs`：项目文档、中间分析、设计资料和调研结果；
* `./local_scripts`：临时测试、数据处理或一次性验证脚本；
* `./tests`：正式测试；
* 根级与模块级 `DEV_OVERVIEW.md`：方向文档树；
* 根级与模块级 `PRD.md`：需求文档树。

`./local_scripts` 默认通过 `.git/info/exclude` 忽略：

```gitignore
local_scripts/
```

除非脚本已成为正式工具，否则不要迁入生产目录。

### 个人文件双 Git

项目可在根目录使用 `.personal-git/` 保存第二套 Git 元数据，与项目 Git 共享工作区，但两者的 tracked file set 必须互斥。个人 Git 仅监管：

* 任意层级的 `*PRD.md`、`AGENTS.md`、`PROJECT_IMPROVEMENTS.md`、`DEV_OVERVIEW.md`、`tasks.md`；
* 根目录下的 `.codex/`、`local_scripts/`、`local_docs/`。

项目 Git 通过自身 `info/exclude` 忽略上述个人文件及 `.personal-git/`；个人 Git 使用自己的 `info/exclude` 默认忽略其他项目文件。普通项目 Git 提交不得纳入个人文件，也不得把已由一方跟踪的文件静默交给另一方。

需要初始化、查看、提交、切支对齐、撤销或按项目版本回退个人文件时，调用 `$personal-git`。正常写入前，个人 Git 必须切换到与当前项目分支同名的分支；新分支从已确认来源的个人快照建立，不得让所有项目分支共用一个个人分支。每个正常的个人 Git 提交必须包含 `Project-Anchor: <项目 Git HEAD 的完整 SHA>`；回退只在对应个人分支内按锚点定位，不跨分支搜索兜底。detached HEAD 不自动创建或选择个人分支；每个项目 worktree 使用其根目录下独立的 `.personal-git/`。不得在含 `.personal-git/` 的项目中使用会忽略 exclude 规则的 `git clean -x` 或 `git clean -X`。

## 十四、代码风格

* 代码简洁、清晰、易读；
* 修改既有代码时优先遵循当前项目风格；
* 函数与脚本包含必要的 docstring 和关键注释；
* 合理补充完整类型注解，除非必要避免 `Any`；
* 注释解释“为什么”，不逐行复述代码；
* 避免隐藏副作用、无必要的全局状态和过深嵌套；
* 优先局部修改和清晰接口，不为不确定扩展提前设计；
* 不顺带格式化或重写无关文件。

## 十五、完成总结

每次完成开发任务后，应向用户说明：

* 完成了哪些修改；
* 涉及哪些核心文件；
* 读取了哪些相关 `DEV_OVERVIEW` 和 PRD；
* PRD“已实现”如何更新；
* PRD“未实现”是否调整及具体内容；
* `DEV_OVERVIEW` 是否更新及原因；
* 执行了哪些测试或验证及结果；
* 当前风险、疑问或后续建议。

如果只执行 `$dev-commute` 而没有开发代码，应说明：

* 更新了哪些方向性内容；
* 是否同步更新 PRD“未实现”；
* 是否存在冲突或待确认事项；
* 本次没有进行代码实现或测试。
