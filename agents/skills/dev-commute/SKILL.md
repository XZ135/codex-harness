# Dev Commute

将用户沟通中的项目级背景与开发方向沉淀为可持续维护的仓库文档，并在必要时同步形成尚未实现的细化需求。

本 skill 只负责上下文识别、冲突检查和文档同步。它不把方向沟通自动解释为开发授权，也不在 skill 阶段修改业务代码。

## 核心结果

每次执行应得到以下一种或多种结果：

1. 将方向性信息融入相关 `DEV_OVERVIEW.md`；
2. 将已确认的细化需求融入相关 `PRD.md` 的“未实现”部分；
3. 发现与既有方向或需求的冲突，并在写入前请求用户确认；
4. 判断当前沟通不应沉淀，并说明原因；
5. 若同一请求还包含明确开发任务，在文档同步完成且不存在冲突后，退出 skill 阶段并按 `AGENTS.md` 的开发流程继续。

## 工作边界

必须遵守以下边界：

* 不修改业务代码、测试、依赖或运行配置；
* 不更新 PRD 的“已实现”部分；
* 不把未确认的想法写成正式方向或需求；
* 不把 `DEV_OVERVIEW` 变成 backlog、排期表或开发日志；
* 不把 PRD 的“未实现”内容描述为已排期或承诺交付；
* 不简单追加用户原话，应提炼后融入现有结构；
* 不静默覆盖与新沟通冲突的既有要求；
* 不为了建立文档而虚构项目背景、模块职责或验收标准。

## 执行流程

### 1. 识别本次沟通中的信息层级

从用户当前请求和必要的对话上下文中分别提取：

* **方向级信息**：项目背景、目标、定位、跨模块原则、整体架构边界、长期约束、优先级变化或未来发展方向；
* **需求级信息**：具体功能、业务规则、接口、数据结构、行为边界、依赖、验收标准或开发计划细节；
* **立即开发要求**：用户是否同时要求现在开始实现；
* **待确认内容**：可能存在多种解释、与既有文档冲突或尚未形成明确结论的部分。

只沉淀对后续开发持续有价值的信息。一次性的讨论过程、措辞尝试和低层实现猜测不进入正式文档。

### 2. 定位仓库与适用规则

确认仓库根目录：

```bash
git rev-parse --show-toplevel
```

读取仓库中适用的 `AGENTS.md` 或 `AGENTS.override.md`，遵循更具体的项目规则。

定位方向文档：

```bash
find . -name "DEV_OVERVIEW.md" \
  -not -path "./.git/*" \
  -not -path "./.venv/*" \
  -not -path "./node_modules/*"
```

定位需求文档：

```bash
find . -name "PRD.md" \
  -not -path "./.git/*" \
  -not -path "./.venv/*" \
  -not -path "./node_modules/*"
```

根据目录层级、模块范围和文档内容选择相关文件，不要只凭文件名判断。

读取顺序：

1. 根级 `DEV_OVERVIEW.md`；
2. 相关子级 `DEV_OVERVIEW.md`；
3. 根级 `PRD.md`；
4. 相关子级 `PRD.md`；
5. 必要的 README、代码或接口定义，仅用于确认文档上下文，不进入实现。

### 3. 检查新信息与既有文档的一致性

逐项比较用户新沟通与现有文档：

* 是补充、细化、替换还是撤销既有方向；
* 是否与 PRD 的“已实现”行为冲突；
* 是否与 PRD 的“未实现”要求冲突；
* 是否会改变模块职责、接口边界或项目目标；
* 用户是否明确表达了覆盖关系。

处理规则：

* 用户明确说明“替换、取消、改为、不再采用”等覆盖关系时，可按其最新明确要求更新，并移除或改写失效内容；
* 只是可能冲突、范围不清或无法判断覆盖关系时，先向用户提出简洁、结构化的确认问题，在确认前不要写入冲突内容；
* 低风险且不改变原意的补充可以直接融合；
* 不通过“同时保留两种互斥说法”来回避冲突。

### 4. 决定写入目标

使用以下归属规则：

| 信息类型 | 写入位置 |
|---|---|
| 项目背景、整体目标、长期方向 | `DEV_OVERVIEW.md` |
| 跨模块原则、全局架构约束、项目级优先级 | `DEV_OVERVIEW.md` |
| 已确认但不一定立即实施的整体调整 | `DEV_OVERVIEW.md` |
| 具体功能、行为规则、接口与数据约束 | PRD“未实现” |
| 验收标准、依赖关系、明确的开发计划细节 | PRD“未实现” |
| 尚未明确的关键选择 | 对应文档的待确认事项，或先询问用户 |
| 单纯实现方法猜测、临时讨论、普通问答 | 不写入 |

同一沟通可以同时更新两类文档，但应分别按各自颗粒度表达，不能在两个位置复制同一段正文。

### 5. 更新 DEV_OVERVIEW

若根级 `DEV_OVERVIEW.md` 不存在且本次确有项目级方向需要记录，则创建该文件。

推荐最小结构：

```markdown
# DEV_OVERVIEW

## 项目背景

## 当前目标与开发方向

## 全局原则与约束

## 中长期方向

## 关键未知与待决策事项

## 子文档索引
```

更新要求：

* 将新内容整合到最合适的现有章节；
* 使用稳定、面向未来的表述，不记录对话过程；
* 保留“这是方向而非立即排期”的语义；
* 明确跨模块影响和长期约束，但避免下沉到函数级实现；
* 删除已经被明确替代的旧描述；
* 若内容只适用于特定模块且已达到独立维护规模，创建子级 `DEV_OVERVIEW.md`，并在父级增加索引；
* 不因少量新增内容过早拆分文档树。

### 6. 更新 PRD 的“未实现”部分

只有当用户给出了已确认且足够具体的需求信息时才更新 PRD。

若相关 PRD 不存在，可创建最小结构：

```markdown
# <项目或模块> PRD

## 上下文与范围

## 已实现

## 未实现

## 子文档索引
```

更新要求：

* 只修改“未实现”及必要的范围或索引内容；
* 不因本次沟通修改“已实现”状态；
* 用可执行、可验证的需求语言表达；
* 区分已确认要求与待确认问题；
* 记录必要的行为边界、依赖和验收标准；
* 不提前固化无必要的类名、函数名或内部代码结构；
* 不把“未实现”描述为已经排期；
* 若新要求替代旧的未实现要求，应改写或删除失效内容，避免同时保留互斥版本；
* 若旧 PRD 尚未分区，只迁移本次涉及的内容即可，不扩大为无关的全量重构。

### 7. 检查文档树与 diff

完成写入后检查：

* 新内容是否放在正确层级；
* 根文档是否需要新增子文档索引；
* 是否出现重复、矛盾或过期表述；
* PRD 是否清楚区分“已实现”和“未实现”；
* 是否误把未实现内容写成完成事实；
* skill 阶段是否只修改了允许的文档文件。

使用 `git diff` 检查实际改动。根据仓库情况限定路径，例如：

```bash
git diff -- DEV_OVERVIEW.md PRD.md '**/DEV_OVERVIEW.md' '**/PRD.md'
```

若 shell 的 glob 行为不可靠，先用 `git diff --name-only` 获取文件，再逐个检查。

### 8. 处理同时存在的开发要求

如果用户在同一请求中既提供了新的整体方向，又明确要求立即开发：

1. 先完成本 skill 的文档定位、冲突检查和必要同步；
2. 若新方向与现有文档冲突且覆盖关系不清，先请求确认，不进入开发；
3. 若没有冲突，或用户已明确新要求覆盖旧要求，结束 skill 阶段；
4. 按 `AGENTS.md` 重新读取相关 `DEV_OVERVIEW` 与 PRD，并继续正常开发流程；
5. 开发完成后的“已实现”迁移和剩余“未实现”调整由正常开发流程负责，不在本 skill 阶段提前处理。

## 输出要求

完成后向用户明确报告：

* 读取了哪些相关方向和需求文档；
* 更新了哪些 `DEV_OVERVIEW.md`；
* 新增、修订或移除了哪些项目级方向；
* 是否更新了 PRD 的“未实现”部分，以及具体条目；
* 哪些信息没有记录及其原因；
* 是否发现冲突、歧义或待确认事项；
* 是否创建了新的子文档或索引；
* 本 skill 阶段没有进行哪些代码实现或测试。

不要只说“文档已更新”。必须让用户能够判断 Codex 是否正确理解并沉淀了本次沟通。
