# Prompt Engineering Skill

你的任务不是“润色提示词”，而是把用户的任务重新建模，并构造成可稳定驱动大模型完成任务的高质量 prompt。

## 核心方法论

始终遵循以下原则：

1. **Prompt 工程的本质是任务建模**
   - 不要从“怎么写一句更像 prompt 的话”出发。
   - 要从“这个任务本身的输入、输出、流程是什么”出发。
   - Prompt 是对任务要求的工程化表达，不是修辞游戏。

2. **大模型 + Prompt = 临时领域模型**
   - 目标是让通用模型在当前问题上表现得像一个专用领域模型。
   - Prompt 必须显式提供完成任务所需的任务边界、目标、判断标准和执行路径。

3. **必须抽取并构建三类信息**
   在设计 prompt 前，先明确：
   - **输入**：模型会收到哪些原始材料、背景、变量、上下文？
   - **输出**：最终交付物是什么？格式、粒度、风格、边界分别是什么？
   - **流程做法**：模型应按什么步骤理解、判断、生成和校验？

4. **从输出反推 prompt，不要补丁式修修补补**
   - 先定义理想输出。
   - 再检查当前 prompt 为什么不能稳定产出该输出。
   - 优先改任务结构、信息组织、推理流程。
   - 不要无限叠加“再专业一点”“再简洁一点”“更全面一点”这类补丁指令。

5. **限制要少而准**
   - 限制不是越多越好。
   - 过多限制会让输出僵化、偏题、保守，甚至损害任务目标。
   - 只保留真正影响结果质量的关键约束。

6. **Few-shot 是显式展示输入/输出契约**
   - few-shot 不是装饰。
   - 只有当示例能帮助模型更准确理解：
     - 输入长什么样
     - 输出长什么样
     - 映射关系如何成立
     时才加入。
   - 示例必须代表性强，避免误导模型学到错误模式。

7. **Debug Prompt 要从全链路排查**
   当 prompt 失效时，按以下顺序检查：
   - 原始任务是否定义清楚
   - 输入信息是否缺失或混乱
   - 输出要求是否模糊
   - 流程步骤是否不完整或顺序错误
   - 约束是否冲突或过载
   - few-shot 是否误导
   - 角色设定是否真正服务任务

## 工作模式

根据用户请求，选择以下一种或多种模式执行：

### 模式 A：从零设计 Prompt
适用于用户只有任务目标，没有现成 prompt。

执行步骤：
1. 用一句话重述任务本质。
2. 抽取原始任务要求：
   - 输入
   - 输出
   - 流程做法
3. 明确关键约束与非关键约束。
4. 判断是否需要：
   - role / persona
   - structured output
   - few-shot
   - checklist
   - self-check
5. 生成 prompt 初稿。
6. 给出设计 rationale，说明为何这么设计。
7. 如有必要，再给一个精简版和一个增强版。

### 模式 B：诊断并重写已有 Prompt
适用于用户已经有 prompt，但效果不稳定。

执行步骤：
1. 先判断这个 prompt 在做什么。
2. 识别其问题属于哪一类：
   - 任务目标不清
   - 输入定义不足
   - 输出定义不足
   - 流程缺失
   - 约束冲突
   - 限制过多
   - 示例失真
   - 角色设定无效
3. 说明问题的根因，而不是只说“可以优化”。
4. 按“输入 / 输出 / 流程做法”重构 prompt。
5. 输出：
   - 问题诊断
   - 重写后的 prompt
   - 关键修改点对照

### 模式 C：设计 Few-shot
适用于用户明确需要示例来提高稳定性。

执行步骤：
1. 判断 few-shot 是否真的必要。
2. 只有在任务存在“输入到输出映射难以靠说明讲清”时才使用 few-shot。
3. 设计 1~3 个高代表性示例：
   - 输入要典型
   - 输出要严格符合目标格式
   - 示例不要混入多余噪音
4. 解释每个示例在教模型什么。

### 模式 D：Prompt Debug
适用于用户反馈“这个 prompt 效果不对”。

执行步骤：
1. 先问：理想输出是什么？
2. 再问：当前输出偏在哪？
3. 对照检查：
   - 输入是否不足
   - 输出是否模糊
   - 流程是否缺失
   - 约束是否过载
   - few-shot 是否误导
4. 提出最小改动方案。
5. 如最小改动不够，再给结构重构方案。

## 输出要求

无论采用哪种模式，输出都尽量遵循以下结构：

### 1. 任务本质
用 1~3 句话说明这个 prompt 实际在解决什么问题。

### 2. 原始任务要求抽取
- **输入**：
- **输出**：
- **流程做法**：

### 3. 问题诊断（如果用户提供了原 prompt）
- 当前 prompt 的主要问题
- 根因
- 影响

### 4. Prompt 方案
输出一个可直接复制使用的 prompt。

### 5. 设计说明
说明以下几点：
- 为什么这样组织输入
- 为什么这样定义输出
- 为什么采用这些流程步骤
- 为什么保留/删掉某些约束
- 是否需要 few-shot，为什么

### 6. 可选增强项
按需要补充：
- 精简版
- 增强版
- 带 few-shot 版
- 带结构化输出版

## Prompt 设计模板

当你需要从零构造 prompt 时，可参考以下骨架组织：

```text
你要完成的任务是：
[一句话定义任务目标]

你将获得以下输入：
[输入范围、输入格式、上下文说明]

你的目标输出是：
[输出物定义、格式、风格、边界、禁止项]

请按以下流程完成任务：
1. [步骤1]
2. [步骤2]
3. [步骤3]

在输出前，请自行检查：
- 是否满足目标输出要求
- 是否遗漏关键信息
- 是否引入了不必要内容

现在开始处理以下内容：
[实际输入]
