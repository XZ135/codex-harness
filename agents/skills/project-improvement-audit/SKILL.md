# Project Improvement Audit

当用户要求记录、检查、列举或修复项目中的可优化方面、技术债、重构机会、测试缺口、架构问题、性能问题、安全风险、可维护性问题或开发体验问题时，使用本 skill。

## 默认语言

默认使用中文，包括 `PROJECT_IMPROVEMENTS.md`、对话总结、新增优化项说明、修复说明和未修复原因说明。除非用户明确要求使用其他语言。

## 记录文件

在项目根目录维护：

```text
PROJECT_IMPROVEMENTS.md
```

不要使用表格格式。使用分节格式记录每个优化项。

推荐结构：

```markdown
# 项目可优化项记录

本文件用于记录项目中已发现的可优化方面，并在后续检查和修复中持续更新状态。

## 状态说明

- `open`：仍然存在，尚未修复
- `fixed`：已确认修复
- `obsolete`：已不再适用
- `deferred`：确认存在，但暂缓处理

## 优化项

### IMP-001 - 示例标题

- 状态：open
- 分类：maintainability
- 严重级别：medium
- 首次发现：YYYY-MM-DD
- 最近检查：YYYY-MM-DD
- 修复时间：
- 证据：具体文件、模块、命令结果或项目结构证据
- 原因/影响：为什么这是一个需要关注的优化项
- 建议：可以如何改进

## 检查记录

### YYYY-MM-DD

- 复查了 X 个已有优化项
- 标记修复 X 个
- 新增 X 个优化项
- 仍未解决 X 个

## 修复记录

### YYYY-MM-DD

- 修复了 X 个优化项
- 涉及文件：
- 验证方式：
```

如果现有文件是表格格式，应在保留原有信息的前提下转换为上述分节格式。

## 使用模式判断

根据用户措辞选择模式。优先级如下：

1. 用户要求修复、优化、处理某个已有编号或具体问题 → 进入优化/修复模式。
2. 用户明确描述某个具体问题，并要求记录、加入、记一下、新增待优化项，但没有要求立即修复 → 进入记录模式。
3. 用户要求检查、扫描、审计、review 项目 → 进入检查模式。
4. 用户要求列举、展示、查看当前未修复项 → 进入列举模式。

当用户同时提出多个意图时，优先遵循更具体的动作。例如：

* “记录一下 README 缺少环境变量说明” → 记录模式
* “检查项目还有哪些问题” → 检查模式
* “列举当前 open 项” → 列举模式
* “修复 IMP-002” → 优化/修复模式
* “记录这个问题并顺手修掉” → 优化/修复模式，并确保该问题已被记录或能映射到已有优化项

## 0. 记录模式

当用户调用本 skill 时，如果明确描述了某个具体问题、待优化内容、技术债、风险点或改进建议，但没有要求立即修复，也没有要求全面检查项目，则进入记录模式。

触发示例：

* 记录一个优化项：README 里缺少环境变量说明
* 把这个问题记到优化项里：`src/config.ts` 里有硬编码配置
* 新增一个待优化项：当前缺少接口测试
* 记一下：当前 Docker 部署文档不完整
* 这里有个技术债：订单查询可能有 N+1 问题

记录模式目标：理解用户描述的具体问题，并将其作为新的优化项记录到 `PROJECT_IMPROVEMENTS.md` 中。

记录模式默认只新增记录，不扫描整个项目，不修改代码，不修复问题，除非用户明确要求。

执行步骤：

1. 定位项目根目录，优先使用 Git 根目录。
2. 读取 `PROJECT_IMPROVEMENTS.md`，不存在则创建。
3. 理解用户描述的问题或待优化内容。
4. 判断是否已有重复或高度相似优化项：

   * 如果已有，不新增重复项，可更新已有项的证据、原因/影响或建议。
   * 如果已有项状态为 `fixed` 或 `obsolete`，但用户提供新证据表明问题仍存在，应重新判断并说明处理方式。
5. 如果不是重复项，则新增优化项。
6. 编号使用 `IMP-001`、`IMP-002` 格式，并从现有最大编号继续。
7. 补全字段：标题、状态、分类、严重级别、首次发现、最近检查、修复时间、证据、原因/影响、建议。
8. 如果用户信息不足，优先基于项目上下文合理补全；仍无法判断时，向用户确认；不要新增模糊项。
9. 在“检查记录”中追加本次记录摘要，或新增“记录记录”。

记录完成后，在对话中说明：

```markdown
## 本次记录结果

### 新增优化项

- IMP-XXX - 标题
  - 分类：
  - 严重级别：
  - 证据：
  - 建议：

### 未新增或合并到已有项

- IMP-YYY - 标题
  - 原因：
  - 更新内容：

文档路径：PROJECT_IMPROVEMENTS.md
```

如果没有新增优化项，明确说明原因，例如：

```markdown
本次没有新增优化项，因为该问题已存在于 IMP-XXX 中，已更新该项的证据和建议。
```

## 1. 检查模式

当用户使用以下表达时，进入检查模式：

* 检查
* 扫描
* 审计
* review
* audit
* 看看还有哪些可优化项
* 更新优化项记录

检查模式目标：复查已有优化项、发现新增优化项，并更新 `PROJECT_IMPROVEMENTS.md`。

执行步骤：

1. 定位项目根目录，优先使用 Git 根目录。
2. 读取 `PROJECT_IMPROVEMENTS.md`，不存在则创建。
3. 复查已有 `open` 和 `deferred` 优化项。
4. 对已有优化项：

   * 有明确证据表明已解决时，标记为 `fixed`
   * 相关代码、模块或方向已不存在时，标记为 `obsolete`
   * 否则保持原状态
   * 更新“最近检查”为今天日期
5. 扫描当前项目，寻找新的可优化项。
6. 新增项必须具体、可执行、非重复。
7. 编号使用 `IMP-001`、`IMP-002` 格式，并从现有最大编号继续。
8. 更新“检查记录”。

检查模式默认不修复代码，除非用户明确要求。

检查完成后，必须说明：

* 复查了多少个已有优化项
* 标记修复了多少个
* 新增了多少个
* 仍然未修复的有多少个
* 文档路径

如果有新增优化项，逐项说明：

```markdown
## 本次新增优化项

### IMP-XXX - 标题

- 分类：
- 严重级别：
- 为什么新增：
- 具体证据：
- 建议处理方式：
```

如果没有新增优化项，明确说明：

```markdown
本次没有发现新的可优化项。
```

## 2. 列举模式

当用户使用以下表达时，进入列举模式：

* 列举
* 展示
* 查看
* list
* show
* 当前有哪些未修复项
* 还有哪些 open 项
* 有哪些待优化项

列举模式目标：从 `PROJECT_IMPROVEMENTS.md` 中列出当前尚未修复的优化项。

列举模式默认只读取文档，不扫描新问题，不修改代码，不更新状态。

列出范围：

* `open`
* `deferred`

默认不列出：

* `fixed`
* `obsolete`

输出时按严重级别和编号排序：

1. `high`
2. `medium`
3. `low`

输出格式：

```markdown
## 当前未修复优化项

### IMP-XXX - 标题

- 状态：
- 分类：
- 严重级别：
- 原因/影响：
- 证据：
- 建议：
```

列举结束后，提示用户可以指定要处理的项，例如：

```text
你可以指定要优化的编号，例如：处理 IMP-002 和 IMP-005。
```

## 3. 优化/修复模式

当用户明确要求优化、修复或处理具体优化项时，进入优化/修复模式。

触发示例：

* 优化 IMP-001
* 修复 IMP-002 和 IMP-004
* 处理第 1、3 项
* 把这些 open 项修掉
* 解决 documentation 相关的问题

优化/修复模式目标：根据用户指定范围修改项目，并更新 `PROJECT_IMPROVEMENTS.md` 中对应项的状态。

执行步骤：

1. 读取 `PROJECT_IMPROVEMENTS.md`。
2. 识别用户指定的优化项范围。
3. 如果用户指定不清楚，优先根据上下文推断；仍无法判断时，向用户确认。
4. 阅读相关代码和文档。
5. 制定最小必要修改方案。
6. 执行修改。
7. 运行相关验证命令，例如测试、lint、类型检查或构建。
8. 只有在修复完成并有验证证据时，才将对应项标记为 `fixed`。
9. 更新对应项：

   * 状态：fixed
   * 最近检查：今天日期
   * 修复时间：今天日期
   * 证据：说明已修改的文件和验证结果
10. 在“修复记录”中追加本次修复摘要。

如果某项尝试修复但未能完全完成，不要标记为 `fixed`。应保留 `open`，并更新证据或建议，说明剩余问题。

修复完成后，必须说明：

```markdown
## 本次处理结果

### 已修复

- IMP-XXX - 标题
  - 修改内容：
  - 涉及文件：
  - 验证方式：

### 未完成或仍需处理

- IMP-YYY - 标题
  - 原因：
  - 建议下一步：
```

## 检查范围

检查模式下重点关注：

* 重复代码、过长函数、过大文件
* 模块边界不清晰、职责混杂、耦合过高
* 异常处理、输入校验、边界情况处理不足
* 关键路径缺少测试
* 测试质量低、断言弱、回归覆盖不足
* 配置硬编码、环境变量说明缺失
* README、启动说明、部署说明不完整
* 可能的安全风险，例如密钥泄露、路径处理不安全、命令执行不安全
* 低效查询、循环调用接口、重复计算、潜在性能瓶颈
* 脚本、依赖管理、开发启动流程不清晰

忽略以下目录，除非用户特别要求：

```text
.git
node_modules
dist
build
coverage
.cache
.next
.venv
venv
__pycache__
target
```

## 新增优化项要求

每个新增优化项必须包含：

* 标题
* 状态
* 分类
* 严重级别
* 首次发现
* 最近检查
* 修复时间
* 证据
* 原因/影响
* 建议

分类优先使用：

```text
code-quality
architecture
testing
reliability
performance
security
maintainability
documentation
configuration
developer-experience
dependency-management
```

严重级别使用：

* `high`：可能导致明显 bug、安全风险、生产故障或严重维护风险
* `medium`：有明确项目影响的质量、可靠性、测试或维护问题
* `low`：较小的清理、文档或开发体验问题

## 证据规则

证据必须具体。

好的证据示例：

* `src/config.ts` 使用了环境变量，但 `README.md` 未说明 required env
* `src/services/user.ts` 和 `src/api/user.ts` 存在重复校验逻辑
* `package.json` 存在 test script，但未发现测试文件
* `src/db/query.ts` 在循环中执行数据库查询，可能形成 N+1 查询

不要新增模糊项，例如：

* “代码质量可以提升”
* “架构有点乱”
* “测试可能不够”

## 安全规则

* 不删除历史优化项
* 不泄露密钥、token、密码等敏感值
* 不运行破坏性命令
* 不在没有明确证据时标记为 `fixed`
* 不在列举模式中扫描新问题或修改文件
* 不在检查模式中直接修复代码，除非用户明确要求
* 宁可少报，也不要添加大量低质量、泛泛而谈的优化项
