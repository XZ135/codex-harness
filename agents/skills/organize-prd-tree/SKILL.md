# Organize PRD Tree

审计并整理项目的 PRD 文档树，使每条需求具有清晰、稳定且唯一的归属，同时保持项目方向、需求语义和实现状态不被结构调整意外改变。

本 skill 负责文档结构治理，不负责实现功能、重新定义产品需求或判断开发优先级。

## 受保护内容

整理过程中始终保护以下内容：

* 用户已确认的需求语义、边界和验收标准；
* PRD 中“已实现 / 未实现”的状态归属；
* 已存在的需求编号、外部引用和可追踪标识；
* `DEV_OVERVIEW.md` 中的项目级方向和跨模块约束；
* 尚未解决的冲突、疑问和待确认事项。

除非用户在当前请求中明确授权，不得借整理之名：

* 新增、取消或改变需求；
* 将内容从“未实现”改为“已实现”，或反向移动；
* 根据代码猜测未标注需求的实现状态；
* 改变模块职责、接口边界或产品方向；
* 修改业务代码、测试、依赖或运行配置；
* 把整理过程写成长篇日志或历史记录。

若发现实质性冲突，不自行选择其中一种说法。保留冲突信息，将其归入适当的“待确认”位置，并在结果中明确报告。

## 默认范围

* 用户指定目录或模块时，只整理该范围及其必要的父级索引；
* 用户只调用 skill 而未指定范围时，整理当前 Git 仓库的完整 PRD 树；
* 只把名为 `PRD.md` 的文件视为 PRD 节点，除非仓库的适用 `AGENTS.md` 明确规定了其他命名方式；
* 允许机械修复其他 Markdown 文档中因 PRD 移动产生的相对链接，但不得修改这些文档的业务含义；
* 不创建与任务无关的 README、迁移日志或备份文件。临时审计结果放在系统临时目录，不提交到仓库。

## 执行流程

### 1. 确认仓库、规则和工作区状态

确认仓库根目录：

```bash
git rev-parse --show-toplevel
```

读取适用的 `AGENTS.md` 或 `AGENTS.override.md`，再读取：

1. 根级及相关子级 `DEV_OVERVIEW.md`；
2. 根级及整理范围内的全部 `PRD.md`；
3. 必要的 README 或其他文档，只用于确认目录职责和链接关系。

检查工作区：

```bash
git status --short
```

不得重置、覆盖或丢弃用户已有改动。若 PRD 已有未提交修改，将其视为当前文档事实并纳入整理。

若当前目录不是 Git 仓库，仍可整理，但使用临时快照代替 `git diff` 完成前后检查。

### 2. 生成 PRD 树审计

优先运行本 skill 附带的只读审计脚本：

```bash
python <skill-directory>/scripts/audit_prd_tree.py \
  --root <repository-root> \
  --format markdown
```

该脚本只读取文件，输出以下机械检查结果：

* PRD 路径、行数、标题和状态章节；
* 父子 PRD 关系及父级索引缺失；
* 失效的相对 Markdown 链接；
* 完全重复的长段落；
* 可能需要人工审查的超长文档。

脚本结果只是线索，不得仅凭行数或重复检测自动拆分、合并或删除内容。

### 3. 建立当前需求归属图

对每个 PRD 识别：

* 文档负责的业务域、系统、模块或能力边界；
* 父级上下文和下级子域；
* “已实现”“未实现”和待确认内容；
* 跨模块需求、共享约束和依赖；
* 与其他 PRD 重复、冲突或互相引用的内容；
* 当前索引关系和文档链接。

为整理范围建立临时迁移映射。至少记录：

| 原文件与章节 | 处理方式 | 目标文件与章节 | 原因 |
|---|---|---|---|
| `path/PRD.md#章节` | 保留 / 移动 / 合并 / 标记冲突 | `target/PRD.md#章节` | 模块归属或重复关系 |

每个原有需求章节都必须有去向。不得在没有迁移映射的情况下大面积重写。

### 4. 制定结构方案

优先按照稳定的产品或模块边界组织文档，而不是按照当前篇幅平均切分。

#### 拆分条件

满足以下一项或多项时，考虑创建子 PRD：

* 文档同时维护多个可以独立演进、验收或分配职责的模块；
* 某一子域具有独立接口、数据模型、业务规则或依赖边界；
* 根级 PRD 已承载大量模块细节，难以发挥总览和索引作用；
* 同一模块的“已实现 / 未实现”内容散落在多个不相邻章节；
* 文档已明显妨碍定位和更新，且存在自然的语义边界。

行数只能作为审查信号：约 500 行以上应重点检查，约 800 行以上通常是强拆分候选，但若内容仍属于单一不可分割边界，不得机械拆分。

#### 合并条件

满足以下情况时，考虑合并：

* 子 PRD 没有独立职责，只是父 PRD 的少量延伸；
* 两个 PRD 实际维护同一模块或同一组需求；
* 子文档长期只有极少内容，且不存在独立演进价值；
* 当前拆分造成同一需求必须在多个文件中同步维护。

不要为了减少文件数量合并职责明确的模块，也不要创建只有一两个普通条目的微型 PRD。

#### 内容归属原则

* 项目级共同需求和跨模块约束放在最近的共同父 PRD；
* 模块专属的功能、接口、数据约束和验收标准放在模块 PRD；
* 每条需求正文只保留一个权威来源；
* 父文档只保留必要摘要和链接，不复制子文档正文；
* 共享依赖通过引用表达，不在多个子 PRD 重复维护；
* 优先沿用仓库现有目录和模块边界，不随意新建中央文档体系；
* 移动文件时优先使用 `git mv`，并修复所有仓库内引用。

### 5. 规范每个 PRD 的结构

除非项目规则另有规定，使用以下最小骨架：

```markdown
# <项目或模块> PRD

## 上下文与范围

## 已实现

## 未实现

## 子文档索引
```

根据实际需要增加“依赖与边界”“待确认事项”等章节，但保持以下规则：

* “已实现”和“未实现”必须清晰分离；
* 同一能力在两个状态下可以分别记录已完成部分和剩余部分；
* 子 PRD 开头说明父级背景、本文件范围及非目标；
* 父级索引使用相对 Markdown 链接，并简述每个子文档的职责；
* 存在更深层子树时，继续使用相同原则，不让根级索引承担全部细节；
* 保留既有需求 ID 和稳定标题；必须改标题时，尽量保留可识别的原术语。

若旧内容没有明确实现状态：

* 不根据措辞自行判定；
* 在文档中保留为“状态待确认”或其他明确的辅助章节；
* 同时补齐空的“已实现 / 未实现”章节；
* 在最终结果中列出需要后续确认的内容。

### 6. 执行低风险迁移

按照迁移映射逐步修改：

1. 先创建目标文档和必要骨架；
2. 再移动需求内容，并保持原状态；
3. 再收缩父文档为项目级需求、必要摘要和索引；
4. 合并完全重复内容时，保留信息更完整、归属更正确的一份；
5. 对语义相近但不完全相同的内容，不做“去重”，而是保留或标记冲突；
6. 更新父子索引和所有受影响的 Markdown 相对链接；
7. 确认目标内容完整后，才删除已被迁空的旧文件。

允许为清晰度进行有限改写，但不得改变需求的条件、范围、强度、优先级或状态。任何可能影响含义的改写都必须在结果中逐项说明。

### 7. 校验需求完整性和状态稳定性

完成结构调整后，逐项检查：

* 迁移映射中的每个原章节是否均已处理；
* 是否有需求只在 diff 中被删除而未在目标位置出现；
* “已实现 / 未实现”之间是否发生未经授权的状态迁移；
* 需求 ID、接口名、数据字段、约束和验收标准是否丢失；
* 重复内容是否真正等价；
* 冲突内容是否被错误合并；
* 每个子 PRD 是否被父级索引；
* 每个子 PRD 是否说明父级上下文和自身范围；
* 所有相对 Markdown 链接是否有效；
* 根级 PRD 是否仍然能够说明项目级需求和导航全树；
* 是否误修改了业务代码、测试、依赖或运行配置。

再次运行审计脚本，并与整理前结果比较。

在 Git 仓库中检查：

```bash
git diff --stat
git diff --name-status
git diff -- '**/PRD.md' 'PRD.md' '**/*.md'
```

不要因 glob 不匹配而忽略根级文件；必要时先使用 `git diff --name-only`，再逐个检查。

### 8. 处理大型 PRD 树

当 PRD 数量很多或总内容很大时，可以使用 subagent 并行完成只读审计，但必须满足：

* 主 agent 先给出统一的项目方向、状态保护和归属规则；
* 每个 subagent 只分析一个明确子树，不独立决定全局结构；
* subagent 返回模块范围、重复项、冲突、拆分或合并候选及风险；
* 主 agent 统一制定迁移映射并负责最终修改；
* 不让多个 agent 同时编辑同一父 PRD 或共享索引。

### 9. 与其他工作流协同

* 当前请求同时引入新的项目方向或长期约束时，先使用 `$dev-commute` 完成方向和未实现需求同步，再执行本 skill；
* 当前请求同时要求开发功能时，先完成 PRD 整理，再重新读取整理后的 `DEV_OVERVIEW` 和 PRD，随后按 `AGENTS.md` 进入开发流程；
* 本 skill 本身不把任何需求标记为已完成，开发后的状态迁移由正常开发流程负责。

## 完成结果

向用户提供可审查的结构化总结，至少包含：

* 整理范围和读取的方向文档；
* 整理前后的 PRD 树结构；
* 新建、移动、合并或删除的文件；
* 主要内容从何处迁移到何处；
* 修复的父子索引和失效链接；
* 合并的完全重复内容；
* 明确保留的冲突、歧义和状态待确认项；
* “已实现 / 未实现”是否发生状态变化；
* 是否对需求措辞做了可能影响理解的调整；
* 实际执行的审计和 diff 校验；
* 本次未修改的业务代码与未执行的业务测试。

不要只报告“PRD 已整理”。应让用户能够确认需求没有在文档重构过程中被遗漏、误删或误改状态。
