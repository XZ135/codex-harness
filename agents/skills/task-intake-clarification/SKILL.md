# Task Intake Clarification

当用户提出较大开发任务、复杂功能改动、架构调整、数据模型调整、接口改造、前后端联动、重构、迁移、工作流改造或多文件修改任务时，使用本 skill。

本 skill 用于 **任务规划前的需求交代与澄清**。目标不是立即制定详细 plan，也不是直接实现代码，而是在进入具体规划前，尽可能基于当前项目理解任务，并与用户核对需求，避免后续实现方向偏离用户真实意图。

## 默认语言

默认使用中文与用户沟通，除非用户明确要求使用其他语言。

## 触发时机

适合使用本 skill 的情况：

* 用户提出新增较大功能
* 用户要求修改现有核心流程
* 用户要求重构、架构调整或模块拆分
* 用户要求调整数据库、API、配置、权限、部署或前后端交互
* 用户描述目标较抽象，例如“优化一下”“升级一下”“改成某种模式”
* 任务可能影响多个模块、多个文件或多类用户行为
* 用户的需求可能存在缺失、歧义或与当前项目实现不一致

不适合使用本 skill 的情况：

* 简单 bug 修复
* 明确的小范围文本、样式或配置修改
* 用户已经给出完整实现细节且任务很小
* 用户明确要求跳过澄清并直接实现

## 工作边界

本 skill 阶段只做：

* 阅读和理解项目
* 梳理用户需求
* 识别影响范围
* 发现不清晰、矛盾或缺失的信息
* 向用户提出关键确认问题
* 输出规划前任务交代结果

默认不做：

* 不直接写详细 implementation plan
* 不直接修改代码
* 不直接创建或删除文件
* 不运行破坏性命令
* 不擅自决定有争议的产品或技术方案

可以执行安全的只读操作，例如查看文件、搜索代码、阅读 README、配置、路由、类型定义、接口定义、测试和相关文档。

## 理解项目的优先级

在提问前，先尽可能基于项目自身信息理解任务。

优先阅读：

1. README、项目说明、开发文档
2. package/依赖/构建配置
3. 路由、入口文件、核心模块
4. 与用户任务相关的现有实现
5. 类型定义、schema、API、数据库模型
6. 测试文件和示例数据
7. 已存在的 TODO、issue、项目约定文档

不要在没有查看项目上下文前提出大量泛泛问题。

## 澄清重点

围绕以下方面判断需求是否清晰：

### 1. 目标与业务意图

确认用户真正想解决什么问题，而不只是表面的实现方式。

需要明确：

* 这个改动要达成什么业务或产品目标
* 面向哪些用户或使用场景
* 当前行为有什么问题
* 期望的新行为是什么

### 2. 范围边界

确认哪些内容包含在本次任务内，哪些不包含。

需要明确：

* 需要改哪些页面、接口、模块或流程
* 是否包含前端、后端、数据库、测试、文档
* 是否需要兼容旧逻辑
* 是否涉及迁移或历史数据处理
* 哪些功能不能被影响

### 3. 当前实现与目标差异

基于项目代码说明：

* 当前项目已经有什么相关能力
* 当前实现和用户目标之间的差距
* 哪些部分可以复用
* 哪些部分可能需要重构或新增

### 4. 输入、输出与数据流

如果任务涉及数据或接口，需要确认：

* 输入数据来自哪里
* 输出结果给谁使用
* 数据结构是否已有约定
* API contract 是否需要变化
* 错误、空数据、异常情况如何处理

### 5. UI / 交互 / 用户体验

如果任务涉及前端，需要确认：

* 用户在哪个页面或入口使用
* 交互流程是什么
* 加载、失败、空状态如何展示
* 是否需要保持现有视觉风格
* 是否有设计稿或参考样式

### 6. 非功能性要求

根据任务判断是否需要确认：

* 性能要求
* 安全要求
* 权限控制
* 日志和可观测性
* 可扩展性
* 兼容性
* 部署和配置要求

### 7. 验收标准

在进入规划前，应尽量明确：

* 什么结果算完成
* 用户会如何验证
* 是否需要测试
* 是否需要 demo 路径
* 是否需要文档更新

## 处理不清晰或矛盾需求

如果发现不清晰、矛盾或缺失信息：

1. 先说明基于项目已理解到什么。
2. 明确指出不清晰或矛盾在哪里。
3. 解释为什么这些点会影响后续规划或实现。
4. 提出少量高价值问题，优先问会影响技术方案和实现范围的问题。
5. 对非关键问题，可以给出默认假设，并请用户确认。

不要一次性提出过多低价值问题。优先区分：

* 必须确认：不确认就可能做错方向
* 建议确认：会影响实现质量或边界
* 可默认假设：影响较小，可以先按合理默认值推进

## 输出格式

完成项目理解后，向用户输出：

```markdown
## 规划前需求确认

### 1. 我对任务的理解

用简洁语言复述用户想做什么，以及这个任务的核心目标。

### 2. 当前项目相关上下文

说明已经从项目中观察到的相关实现、模块、文件、约定或限制。

### 3. 可能影响范围

列出可能涉及的模块、文件类型、数据流、接口、测试或文档。

### 4. 已明确的需求

列出当前已经可以确定的需求点。

### 5. 需要确认的问题

按优先级列出问题：

#### 必须确认

- 问题：
  - 为什么需要确认：
  - 可能影响：

#### 建议确认

- 问题：
  - 为什么建议确认：
  - 默认假设：

### 6. 我建议的默认假设

列出如果用户不补充说明，可以采用的合理默认假设。

### 7. 后续规划所需输入

说明一旦用户确认上述问题，后续 plan 阶段应该基于哪些信息进行具体规划。
```

## 提问原则

* 问题要具体，不要泛泛地问“你想怎么做”
* 优先问会改变实现方向的问题
* 每个问题说明为什么需要确认
* 尽量基于项目现状提出问题
* 不要把项目中已经能确认的信息再问用户
* 如果可以从代码中判断，就先查看代码，不要直接问
* 如果存在多个合理方案，应简要比较后让用户选择
* 如果用户需求明显与项目现状冲突，应明确指出冲突点

## 完成标准

本 skill 完成时，应产出一个清晰的“规划前任务交代结果”，使后续 plan 阶段能够基于以下内容继续：

* 明确的任务目标
* 清楚的范围边界
* 已知项目上下文
* 关键不确定点
* 用户需要确认的问题
* 合理默认假设
* 后续规划所需信息
