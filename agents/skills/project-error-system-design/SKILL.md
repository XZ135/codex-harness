# Project Error System Design

当用户要求构建项目的报错系统、重构异常处理、为某些模块补充错误处理、设计错误类型、错误传播机制、日志机制、错误上下文、降级策略或调试定位机制时，使用本 skill。

默认使用中文与用户交流，除非用户明确要求使用其他语言。

## 核心理解

项目开发与项目执行可以理解为一棵任务执行树。

项目整体任务会被拆分为多个模块。这里的“模块”是广义概念，指一个可独立承担运行职责的代码单元，可以是函数、方法、类、服务、任务节点、流程步骤或多个函数组合，不限于狭义的 Python module。

每个模块都是任务树中的一个节点：

* 模块接收主动配置或外部传入的输入。
* 模块内部执行自己的职责。
* 模块可能调用若干子模块，子模块是当前模块的子节点。
* 子模块产生的结果、错误或中间状态，会影响父模块是否能够完成自己的任务。
* 整个项目的运行结果，是从根节点到各级子节点协作完成的。

因此，报错系统的本质不是简单地“捕获异常”，而是在任意模块无法顺利产生目标返回时，能够准确回答：

* 根源问题发生在哪个最小子模块？
* 这个问题沿着哪条任务路径影响了上层模块？
* 每一级父模块因此产生了什么失败、降级或结果缺失？
* 当前错误对项目整体任务有什么影响？
* 使用者或开发者应该从哪里开始定位和修复？

这里的“路径”指任务执行树中从根模块到根源子模块的调用与责任路径，不是文件系统路径。

## 设计目标

一个好的报错系统应做到：

1. 定位根源
   能识别真正失败的最小子模块，而不是只在最外层返回模糊错误。

2. 表达影响
   能说明该子模块失败后，对父模块、父模块的父模块，以及整体任务造成了什么影响。

3. 保留路径
   能保留从顶层任务到根源错误的完整任务路径，帮助开发者理解错误传播过程。

4. 明确责任边界
   能区分是输入不合法、配置错误、外部依赖失败、数据问题、业务规则不满足，还是代码缺陷。

5. 支持合理处理
   对可预期错误有明确处理策略，例如直接失败、重试、跳过、降级、使用默认值、部分返回或继续执行。

6. 信息准确完整
   错误信息既不能丢失根源，也不能堆叠无意义噪声。应在必要时补充父模块语义，而不是机械重复异常堆栈。

## 模块级报错设计原则

### 1. 先界定模块职责

为任何模块设计错误处理前，必须先理解该模块在项目任务树中的位置：

* 当前模块承担什么任务？
* 它的上游输入来自哪里？
* 它会调用哪些子模块？
* 它的输出会被哪些父模块或后续模块使用？
* 它失败后，对整体任务的影响是什么？
* 它是否是关键路径，还是可选路径、增强路径、缓存路径、辅助路径？

不要在未理解模块职责与调用关系时直接添加 try/except。

### 2. 明确输入契约

每个模块都应明确自己的输入要求，包括：

* 必填字段
* 类型要求
* 值域范围
* 结构要求
* 业务约束
* 配置依赖
* 外部资源依赖
* 前置状态要求

如果某个输入不满足要求，并且可以预见一定会导致后续错误，应在模块入口处尽早校验并失败。

入口校验的目标是把错误定位在正确位置，避免非法输入继续向下传递，最终在更深层模块产生误导性的错误。

输入错误应尽量说明：

* 哪个模块拒绝了输入
* 哪个字段或条件不满足
* 期望是什么
* 实际收到的是什么
* 该错误是否来自用户输入、配置、上游模块或系统状态

### 3. 明确模块允许产生的错误

每个模块不只要定义“成功返回什么”，也要定义“允许失败成什么样”。

应尽量枚举该模块可能遇到的错误类型，例如：

* 输入不合法
* 配置缺失或配置冲突
* 数据为空、缺字段或格式异常
* 外部服务不可用
* 权限不足
* 超时
* 业务规则不满足
* 子模块失败
* 依赖结果不一致
* 不应发生的代码缺陷

对每类错误，需要判断：

* 这是当前模块职责范围内应该处理的错误吗？
* 是否应该继续向上抛出？
* 是否可以降级？
* 是否可以重试？
* 是否应该转换成业务错误？
* 是否需要保留底层原始错误？
* 是否需要增加当前模块语义解释？

### 4. 区分错误处理策略

错误发生后的处理方式本身是项目需求的一部分，不应机械地统一处理。

常见策略包括：

* fail-fast：错误不可恢复，立即失败。
* wrap：保留子模块原始错误，同时补充当前模块语义。
* truncate：截断底层错误，只向上暴露当前模块定义过的错误。
* degrade：使用降级方案继续执行。
* retry：对临时性外部错误进行有限重试。
* skip：跳过非关键子任务。
* partial return：返回部分结果并标记缺失部分。
* default value：使用默认值，但必须记录原因。
* aggregate：多个子模块失败时聚合错误。
* convert：将技术错误转换为业务可理解的错误。

选择策略时要考虑：

* 当前模块是否在关键路径上。
* 错误是否可恢复。
* 子模块错误是否对定位根因有价值。
* 父模块是否需要知道子模块细节。
* 用户或调用方是否适合看到底层错误。
* 是否存在安全、隐私或内部实现泄露风险。
* 项目对部分成功、降级结果或强一致性的要求。

### 5. 保留根因，同时补充父层影响

当子模块错误会导致父模块失败时，父模块不应简单吞掉子模块错误，也不应只原样抛出。

推荐做法是：

* 保留子模块原始错误作为 cause。
* 在父模块中补充当前模块的任务语义。
* 说明子模块失败对父模块造成的影响。
* 形成从父模块到根源模块的错误链。

例如在 Python 中，优先使用：

```python
raise ParentModuleError("父模块执行失败：无法完成 xxx，因为子模块 yyy 失败") from exc
```

这样既保留根源异常，也能表达父模块层面的失败含义。

但不是所有场景都必须暴露完整底层错误。如果底层错误属于内部实现细节、敏感信息或无助于上层处理，可以截断或转换，但应在日志或内部诊断信息中保留足够线索。

## 推荐错误信息结构

如果项目适合结构化错误，优先设计统一错误对象或错误上下文，包含：

* error_code：稳定的错误码
* error_type：错误分类
* message：当前层错误说明
* module：当前模块名或任务节点名
* task_path：从顶层任务到当前错误节点的任务路径
* cause：底层原因
* root_cause：最底层根因摘要
* input_summary：安全脱敏后的关键输入摘要
* impact：该错误对当前模块或整体任务的影响
* recoverable：是否可恢复
* suggestion：建议修复方向
* severity：严重程度
* debug_info：仅供开发或日志使用的诊断信息

不要为了结构化而过度设计。小项目可以先使用异常类 + 错误消息 + 日志上下文；复杂项目再引入统一错误对象、错误码、错误链和错误聚合机制。

## 实现要求

在具体修改代码时，应遵循以下规则：

1. 先阅读现有项目结构
   理解已有异常类、日志系统、返回格式、API 错误格式、测试方式和模块调用关系，不要另起一套不兼容机制。

2. 不要随意吞异常
   禁止使用空的 except、只打印不处理、返回 None 掩盖错误，除非这是明确设计的降级策略，并且有记录。

3. 不要过度捕获
   避免无意义的 broad except。捕获通用异常时，必须有明确目的：补充上下文、转换错误、清理资源、记录日志或降级处理。

4. 保留 cause chain
   在语言支持的情况下，保留异常链。例如 Python 使用 `raise ... from exc`。

5. 错误信息要有模块语义
   每一级父模块添加的信息应解释“当前模块为什么失败”，而不是重复底层报错文本。

6. 输入校验前置
   对确定会导致后续失败的输入问题，应在模块入口校验，而不是等到底层库或子模块产生难以理解的错误。

7. 日志与异常分工明确
   异常用于控制失败路径和向上传递语义；日志用于记录诊断信息。不要用日志替代错误传播。

8. 用户可见信息与开发信息分离
   对外接口返回的信息应简洁、安全、可理解；内部日志可以保留更完整的调用链、输入摘要和堆栈。

9. 测试错误路径
   修改报错系统时，必须补充或更新失败路径测试，包括输入错误、子模块错误、降级路径、异常链和错误消息。

## Codex 工作流程

处理此类任务时，按以下步骤执行：

1. 理解任务执行树
   找出相关模块、父模块、子模块、调用路径和数据流。

2. 界定模块契约
   梳理每个关键模块的输入、输出、职责、前置条件和失败边界。

3. 识别错误类型
   枚举可能错误来源，区分输入错误、业务错误、依赖错误、系统错误和代码缺陷。

4. 设计处理策略
   为每类错误确定 fail-fast、wrap、truncate、degrade、retry、skip、partial return 或 aggregate 等策略。

5. 设计错误传播
   确定哪些错误需要保留原始 cause，哪些需要在父层补充语义，哪些应转换或截断。

6. 落地实现
   按项目现有风格实现异常类、错误码、错误上下文、校验逻辑、日志记录和错误传播逻辑。

7. 补充测试
   为关键失败路径添加测试，验证错误定位、错误链、父层影响说明和降级行为。

8. 总结变更
   向用户说明修改了哪些模块、解决了什么错误定位问题、错误路径如何表达、还有哪些边界需要进一步确认。

## 需要与用户确认的情况

如果错误处理策略涉及项目业务需求，而代码中无法明确判断，应主动向用户确认，例如：

* 某个子模块失败后，整体任务是否必须失败？
* 是否允许返回部分结果？
* 是否允许使用默认值或缓存值？
* 是否需要对用户隐藏底层错误？
* 是否需要暴露详细调试信息？
* 哪些错误属于可恢复错误？
* 哪些模块属于关键路径？
* 错误码或错误格式是否需要与外部 API 协议兼容？

如果用户没有明确要求确认，而代码上下文中已有足够依据，可以基于现有项目风格做合理选择，并在总结中说明依据。

## 反模式

避免以下做法：

* 在最外层统一捕获所有异常，只返回“执行失败”。
* 在每一层重复包装相同错误，导致信息膨胀但没有新增语义。
* 捕获异常后只打印日志，不继续抛出，也不返回明确失败状态。
* 把输入校验全部推迟到底层模块。
* 把子模块错误完全隐藏，导致无法定位根因。
* 把所有错误都暴露给用户，泄露内部实现或敏感信息。
* 不区分业务可预期错误和代码缺陷。
* 没有测试错误路径，只测试成功路径。
* 为了“健壮性”把错误全部降级，导致结果悄悄错误。

## 输出要求

完成任务后，向用户说明：

* 当前报错系统或模块错误处理的设计思路。
* 哪些模块被视为父节点，哪些是子节点。
* 哪些输入被前置校验。
* 哪些错误被包装、截断、降级或直接抛出。
* 如何保留根因与任务路径。
* 新增或修改了哪些测试。
* 如果仍有业务策略不确定，明确列出需要用户决定的点。

整体目标是：让项目在失败时不只是“报错”，而是能够清楚表达“哪里失败、为什么失败、如何影响上层任务、应该从哪里修复”。
